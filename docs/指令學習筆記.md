# 指令學習筆記：從「複製貼上」到「自己會下指令」

> 用 coding-test（Coding 風格測驗）這個專案當教材。
> 讀的順序：先看第 1、2 章建立地圖 → 第 3、4 章查名詞和選擇 → 第 5 章學拿捏範圍 → 第 6 章拆解你下過的指令 → 第 8 章拿去用。

---

## 1. 先看懂一個指令的「骨架」

你下的每個指令都長得像這樣：

```
【功能】要做什麼
【技術】用什麼工具、放在哪
【資料結構】資料長什麼樣子
【Input / Output】進來什麼、出去什麼
【限制】不可以做什麼、一定要做到什麼
【現況】目前已經有什麼
【驗收】怎樣才算做對
```

這不是格式裝飾，每一段都在回答 AI 一個它**猜不到**的問題：

| 區塊 | 回答的問題 | 沒寫會怎樣 | 本專案的例子 |
|---|---|---|---|
| 功能 | 做什麼？ | AI 亂猜範圍 | 「開一支 API：/api/leads」 |
| 技術 | 用哪個工具？ | AI 自己選，可能不是你要的 | 「mongoose，連線字串放 .env.local」 |
| 資料結構 | 資料有哪些欄位？ | 欄位名稱、型別各寫各的 | 「email / answers / result / resultType / createdAt」 |
| Input/Output | 進來和出去的格式？ | 前後端對不起來 | 「Input：email、answers…　Output：成功或失敗」 |
| **限制** | 哪些事一定要/不能做？ | **最容易出事**，AI 會用最省事的做法 | 「同一個 email 要更新，不要重複新增」 |
| 現況 | 已經做了什麼？ | AI 重複造輪子或改壞現有東西 | 「題目在 data/questions.ts，model 已建好」 |
| 驗收 | 怎麼判斷做對？ | 做出「看起來有」但其實沒做到的東西 | 「登出後直接用網址打 API，要打不進去」 |

**核心心法：AI 會做你寫的每一件事，也會「合理地」省略你沒寫的事。**
你的目標不是寫得長，而是把「你心裡知道、但 AI 不知道」的東西寫出來，特別是**限制**和**驗收**。

## 2. 專案地圖：一個網站有哪幾層

```
 使用者的瀏覽器
 ┌──────────────────────────────────────────────┐
 │ ① 前端畫面（app/page.tsx、app/admin/page.tsx）│  ← 看得到的、可以點的
 └───────────────┬──────────────────────────────┘
                 │ 用 fetch「打 API」
 ┌───────────────▼──────────────────────────────┐
 │ ② 後端 API（app/api/**/route.ts）             │  ← 看不到，在伺服器上跑
 │    負責：驗證、判斷、算分、呼叫 OpenAI、存資料  │
 └───────┬───────────────────────┬──────────────┘
         │                       │
 ┌───────▼────────┐     ┌────────▼─────────┐
 │ ③ 資料庫        │     │ ④ 外部服務        │
 │ MongoDB         │     │ OpenAI           │
 │ (models/*.ts)   │     │                  │
 └────────────────┘     └──────────────────┘

 另外兩樣「不在流程裡、但大家都會用到」的東西：
 ⑤ 資料檔 data/questions.ts   → 題目、風格（改主題只改這裡）
 ⑥ 環境變數 .env.local         → 金鑰、連線字串（祕密放這裡）
```

### 為什麼指令要「由下往上」下？

你這 11 個指令的順序不是隨便的，是**從底層往上蓋**：

| 順序 | 做的層 | 為什麼放這個順序 |
|---|---|---|
| 1 建專案 | 地基 | 沒有專案什麼都不能做 |
| 2 資料庫連線 + model | ③ | 後面的 API 都要存取它，先做好才能測 |
| 3 題庫資料檔 | ⑤ | API 要用題目算分，前端要用題目顯示 |
| 4 /api/analyze | ② | 先確認「AI 這關通不通」，**再做畫面** |
| 5 /api/leads | ② | 同上，先確認存得進去 |
| 6 前端流程 | ① | 後端都測過了，才把畫面接上去 |
| 7 管理員登入 | ②+③ | 要保護後台，得先有「誰是管理員」 |
| 8–10 後台、Excel | ①+② | 有了登入才有東西可以保護 |
| 11 美化 | ① | **最後**才修外觀，因為外觀改了不影響功能 |

> **原則：先讓「看不見的」通，再做「看得見的」。**
> 你在第 4、5 步寫的「先不要做畫面，我要先確認這支 API 自己是通的」就是這個意思：
> 畫面壞了你分不清是畫面問題還是 API 問題；API 單獨測通過，之後出錯就只剩畫面可能有問題。

## 3. 名詞表：這個詞是幹嘛的？

### 3-1 專案與工具

| 名詞 | 白話解釋 | 在本專案 |
|---|---|---|
| **Next.js** | 一個「前端 + 後端寫在同一個專案」的框架 | 整個專案都是 |
| **App Router** | Next.js 的路由方式：**資料夾 = 網址** | `app/admin/page.tsx` → 網址 `/admin` |
| **Tailwind** | 用 class 名稱直接寫樣式，不用另外寫 CSS | `className="text-4xl font-bold"` |
| **TypeScript（.ts / .tsx）** | 有「型別檢查」的 JavaScript，打錯欄位名稱會提早報錯 | 所有程式檔 |
| **dev server** | 開發時在你電腦上跑的伺服器（`npm run dev`） | `localhost:3002` |
| **localhost:3002** | 「我自己電腦」的 3002 號門。同時開多個專案會用不同號碼 | 你的其他專案在 3000、3001 |
| **npm / 套件** | 別人寫好的工具包，`npm i xxx` 裝進專案 | mongoose、openai、jose、bcryptjs、xlsx |

### 3-2 資料與資料庫

| 名詞 | 白話解釋 | 在本專案 |
|---|---|---|
| **MongoDB** | 把資料存成一份份「文件」（像 JSON）的資料庫 | 存名單、管理員 |
| **Atlas** | MongoDB 的雲端主機 | 連線字串 `mongodb+srv://…` |
| **Mongoose** | 讓程式用比較好寫的方式操作 MongoDB 的套件 | `lib/mongodb.ts`、`models/` |
| **Schema / Model** | **資料的設計圖**：有哪些欄位、什麼型別、哪些必填 | `models/Lead.ts`、`models/Admin.ts` |
| **欄位 unique** | 這個欄位在整個資料庫不能重複 | Lead 的 email |
| **單例（singleton）** | 整個程式只建立一次連線，之後重複用 | `connectDB()` 把連線存起來 |
| **upsert** | update + insert：有就更新，沒有就新增 | `/api/leads` 同 email 不重複 |
| **分頁（pagination）** | 一次只取一小段，避免資料太多拖垮頁面 | 後台每頁 20 筆 |

### 3-3 API 與前後端

| 名詞 | 白話解釋 | 在本專案 |
|---|---|---|
| **API** | 後端開的一扇「服務窗口」，前端用網址跟它要東西 | `/api/analyze` 等 |
| **route.ts** | Next.js 裡**定義一支 API** 的檔案 | `app/api/leads/route.ts` |
| **GET / POST** | 「取得資料」/「送出資料」兩種請求方式 | 查名單用 GET，存名單用 POST |
| **fetch（打 API）** | 前端呼叫 API 的動作 | 前端送出 Email 時 |
| **JSON** | 前後端交換資料用的文字格式 | `{ "email": "...", "answers": [...] }` |
| **HTTP 狀態碼** | 後端回覆的「結果代號」 | 200 成功、400 你傳錯、401 沒登入、404 找不到、500 我壞了、502/504 外部服務壞了 |
| **前端 / 後端** | 前端跑在使用者瀏覽器（**使用者看得到、改得動**）；後端跑在你的伺服器（**使用者碰不到**） | 見 4-1 |
| **loading / 錯誤 / 成功 三種狀態** | 任何要「等」的操作都要處理這三種畫面 | 轉圈圈、紅色錯誤、結果頁 |

### 3-4 登入與安全

| 名詞 | 白話解釋 | 在本專案 |
|---|---|---|
| **環境變數 .env.local** | 放祕密（金鑰、密碼）的檔案，**不進 git、不寫死在程式裡** | MONGODB_URI、OPENAI_API_KEY、JWT_SECRET |
| **密碼雜湊（bcrypt）** | 把密碼變成**不可逆**的亂碼再存。資料庫被偷也還原不出密碼 | Admin.passwordHash |
| **JWT** | 一張「簽過名的通行證」。伺服器用 JWT_SECRET 簽章，之後只要驗章就知道你登入過 | 登入成功發給管理員 |
| **cookie** | 瀏覽器自動保存、每次請求自動帶上的小資料 | 通行證放在 cookie |
| **httpOnly** | 設了之後，網頁上的 JavaScript **讀不到**這個 cookie，防偷 | admin_token |
| **後端驗證** | **在後端**檢查你有沒有權限，不是只在畫面上藏起來 | 後台 API 第一步就查 JWT |
| **401 vs 403** | 401 = 你沒登入；403 = 你登入了但沒權限 | 本專案只有一個管理員，所以用 401 |
| **權重** | 每個選項對各風格加幾分，最後比總分 | `data/questions.ts` |

## 4. 「為什麼用這個、不用那個」決策表

### 4-1 最重要的一條：後端驗證 vs 前端隱藏

| 做法 | 能防誰 | 不能防誰 | 結論 |
|---|---|---|---|
| 前端隱藏（按鈕不顯示、頁面不渲染） | 一般使用者 | **任何會用 curl / 瀏覽器開發工具的人** | 只能當「體驗」，**不是安全** |
| 後端驗證（API 檢查 cookie，沒有就回 401） | 所有人 | — | **安全一定靠這個** |

**實例**：第 6 步我最先只在前端把結果藏起來，結果直接 curl `/api/analyze` 還是拿得到分析。
你在驗收寫「沒填 Email 絕對看不到結果」就是要逼出後端驗證。
> **判斷口訣：只要「不讓別人看/做」是重點，就一定要寫「在後端驗證」+「沒有就回 401」+ 驗收「直接用網址打打不進去」。**

### 4-2 其他選擇題

| 情境 | 選這個 | 不選這個 | 為什麼 |
|---|---|---|---|
| 同一個 email 重複填 | **upsert**（更新） | 每次新增 | 不然名單一人多筆，數字不準 |
| 資料庫連線 | **單例**（連一次重複用） | 每次呼叫都重連 | 開發時熱重載會連線爆量、很慢 |
| 題目放哪 | **資料檔 `data/questions.ts`** | 寫死在元件裡 / 放資料庫 | 想換主題只改一個檔；題目不常變，不需要資料庫 |
| 風格代號誰來算 | **後端用權重算** | 讓 AI 判斷 | 結果固定、可重現；AI 只負責寫文字 |
| OpenAI 金鑰放哪 | **後端 + 環境變數** | 前端程式碼 | 前端的東西任何人都能看到，金鑰會被盜刷 |
| 登入憑證存哪 | **httpOnly cookie** | localStorage | 網頁 JS 讀不到，XSS 偷不走 |
| 密碼怎麼存 | **bcrypt 雜湊** | 明文 / 可還原的加密 | 資料庫外洩也看不到原密碼 |
| 建管理員 | **一次性腳本** | 做註冊頁 | 只有你一個管理員，註冊頁反而是漏洞 |
| Excel 在哪產生 | **後端**（xlsx 套件） | 前端組檔 | 後端才能同時驗證登入；資料不必全送到前端 |
| 公開 API 的欄位 | **限制長度、驗證格式** | 全部照單全收 | 公開的 API 會被拿來塞垃圾 |
| 失敗訊息 | **寫出具體原因** | 只說「失敗」 | 使用者（和你）才知道要改什麼 |
| 沒資料時的按鈕 | **disabled** | 照常可按 | 避免按了才報錯 |
| 美化的時機 | **功能都通了再做** | 一開始就美化 | 功能還在改時，美化會一直被推翻 |

## 5. 範圍怎麼拿捏：小改、中改、大改

### 5-1 先判斷「這個需求落在哪一層」

| 你想要的 | 它屬於哪一層 | 要動的檔案 | 指令要鎖的範圍 |
|---|---|---|---|
| 換題目、換風格名稱、換主題 | ⑤ 資料檔 | `data/questions.ts` | 「只改這一個檔」 |
| 改文字、顏色、按鈕大小、間距 | ① 前端樣式 | `app/*.tsx`、`globals.css` | 「只調樣式，不動 API 和資料邏輯」 |
| 改畫面流程（多一個步驟） | ① 前端邏輯 | `app/page.tsx` | 「不動 API」 |
| 多存一個欄位（例如姓名） | ③+②+① **三層都要** | model、API、前端 | 要**逐層**講清楚 |
| 改 AI 回答的語氣、字數 | ② 後端（提示詞） | `app/api/analyze/route.ts` | 「只改提示詞」 |
| 加新功能（例如刪除名單） | ②+① | 新 API + 頁面按鈕 | 新功能 = 新指令，附驗收 |
| 部署上線 | 環境 | 主機設定、環境變數 | 獨立的指令 |

### 5-2 三種大小的修改，指令怎麼寫

| 規模 | 特徵 | 指令寫法 | 例子 |
|---|---|---|---|
| **小**（改一個地方） | 你能指出「哪一行、哪個字」 | 直接說**哪個檔、改成什麼** | 「把首頁標題的主色改成綠色」 |
| **中**（一個功能） | 一層裡的一件事 | 用完整骨架（功能/技術/限制/現況） | 第 9 步的後台名單 |
| **大**（跨好幾層） | 資料庫、API、畫面都要動 | **拆成好幾個指令，由下往上**，每步驗收再往下 | 「加姓名欄位」要拆三步 |

### 5-3 拿捏的五條規則

1. **一個指令只做一件事、只動一層。** 你這 11 個指令每個都是一層一件事，這是對的。
2. **用「限制」把範圍鎖住。** 第 11 步「只調樣式，不要動任何 API 和資料邏輯」就是在告訴 AI：就算你覺得 API 可以更好，也不准碰。**不鎖，AI 會順手「幫你改善」，你就不知道它改了哪裡。**
3. **用「現況」告訴它已經有什麼。** 避免它重做、或改壞已經通的東西。
4. **改完先驗收再往下。** 後端用 curl / 瀏覽器測；畫面自己看。確認 OK 才下一個指令。
5. **不確定範圍時，先問再做。** 可以先說「我想做 X，請告訴我會動到哪些檔案，先不要改」，看完再決定要不要執行。

### 5-4 「我該怎麼寫限制」速查

| 你擔心的事 | 寫在限制裡的句子 |
|---|---|
| AI 亂改別的地方 | 「只動 ○○，不要動 △△」 |
| 太早做畫面 | 「先不要做畫面，我要先確認 API 通」 |
| 做太花俏 | 「這一版先不要美化，功能對就好」 |
| 安全 | 「一定要在後端驗證，沒有合法憑證回 401」 |
| 資料不要重複 | 「同一個 email 重複填要更新（upsert）」 |
| 公開的東西 | 「這支 API 任何人都能打，不用登入」 |
| 失敗要看得懂 | 「失敗要回傳可讀的錯誤原因」 |
| 範圍太大 | 「登入做完先停，還不要做後台頁面」 |

## 7. 出狀況時，先看哪裡

| 現象 | 最常見原因 | 怎麼處理 |
|---|---|---|
| 改了 `.env.local` 沒效果 | 環境變數**只在 server 啟動時讀取** | **重啟 dev server** |
| 儲存時 `content of the file is newer` | 檔案被別的程式（例如 AI）改過，編輯器裡是舊版 | 選 Compare 比對，或確認後 Overwrite |
| `querySrv ECONNREFUSED` | 本機 DNS 不回應 MongoDB 的 SRV 查詢 | 專案的 `lib/mongodb.ts` 已有繞路 |
| 網頁是舊畫面 / 一直閃 | 舊分頁卡在重新載入 | 關掉舊分頁、開新的、`Ctrl+Shift+R` |
| 網址打不開 | 埠號不同（3000/3001/3002…） | 看終端機顯示的 Local 網址 |
| API 回 401 | 沒登入或 cookie 過期 | 重新登入；或確認 `JWT_SECRET` 沒被改掉 |
| API 回 400 | 你傳的資料格式不對 | 看回傳的 `message`，裡面寫了哪個欄位錯 |
| API 回 500 / 502 | 後端或外部服務（OpenAI、資料庫）有問題 | 看 `message`，通常寫了原因 |
| 登入後突然被登出 | `JWT_SECRET` 換了，舊通行證全部作廢 | 重新登入即可 |

**排錯順序**：① 看畫面上的錯誤文字 → ② 看終端機（跑 dev server 的視窗）→ ③ 把**完整錯誤訊息**貼給 AI。
越完整越好，「失敗了」和「`status 502, message: OpenAI 超過 30 秒沒有回應`」，後者 AI 一秒就能處理。

## 9. 練習題：用這套邏輯想想看

1. **想在名單多存「姓名」欄位。** 要動哪幾層？該拆成幾個指令？順序是什麼？
   > 提示：model → `/api/leads` → 前端表單 →（要的話）後台表格與 Excel。
2. **想讓管理員可以「刪除」一筆名單。** 這個 API 的限制裡**一定**要寫什麼？驗收怎麼寫？
   > 提示：後端驗證、沒登入回 401、驗收寫「登出後直接用網址打要打不進去」。
3. **想把測驗主題換成「你是哪種咖啡」。** 要動哪個檔？有沒有哪個地方「可能」也要動？
   > 提示：主要是 `data/questions.ts`；但 AI 的提示詞（`/api/analyze`）、首頁文字、網頁標題裡還寫著 Coding，要一併檢查。
4. **結果頁想換成粉紅色。** 屬於哪一層？指令怎麼寫才不會被亂改別的？
5. **想讓外面的人也能用。** 這是哪一類的指令？需要先準備什麼？
   > 提示：部署；要把三個環境變數設到主機、換掉測試用的管理員密碼、考慮登入限流。

## 10. 一頁總結

1. **指令骨架**：功能 → 技術 → 資料結構 → 輸入輸出 → **限制** → 現況 → **驗收**。
2. **順序**：由下往上（資料庫 → API → 畫面 → 美化），**先讓看不見的通，再做看得見的**。
3. **安全**：想擋人，就要在**後端**擋。前端隱藏只是裝飾。
4. **範圍**：一個指令只做一件事、只動一層，用「限制」鎖住範圍。
5. **大需求**：先問「會動到哪些檔」，再拆小步驟，每步驗收。
6. **出錯**：把完整的錯誤訊息貼給 AI，不要只說「壞了」。
